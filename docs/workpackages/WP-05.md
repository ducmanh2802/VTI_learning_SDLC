## Goal

Users can:

- see and accept the current terms;
- turn optional data purposes on and off;
- acknowledge the derivative-risk disclosure;
- export their personal data;
- request account deletion, which a daily job then carries out.

A **terms gate** blocks every other authenticated call until the current TERMS and PRIVACY versions are accepted.

## Design

### SPIs in `shared` (open module)

Every module can implement these without new dependencies:

- `PersonalDataContributor`: `String section()`, `Map<String,Object> export(UUID userId)`.
- `PersonalDataEraser`: `int order()`, `void erase(UUID userId)`.

Implementations in this WP:

- `identity`: exports profile (email, displayName, createdAt, status). Its eraser **scrubs** `core.users`:
  - `email = 'deleted+' || id || '@invalid'`, `password_hash = '!'`;
  - `display_name`, `totp_secret_enc` and `user_secret` set to NULL;
  - `default_alert_channels = '{IN_APP}'`;
  - deletes `refresh_tokens`, `email_tokens`, `security_events`.
- `consent`: exports terms acceptances and consent history. Its eraser sets `ip` and `user_agent` to NULL in `terms_acceptances`. It keeps the rows: they are legal proof and no longer identify the person.

### `identity.api` additions

- `AccountLifecycle.requestDeletion(UUID userId)`: status → `DELETION_REQUESTED`, set `deletion_requested_at`, revoke all refresh tokens.
- `AccountLifecycle.markDeleted(UUID userId)`.
- `PasswordVerifier.matches(UUID userId, String raw)`.
- Publish `identity.api.AccountDeletionRequested(userId)` after the request; it is consumed later (alerting, notification).

### Terms gate (FR-011, FR-012)

- A `OncePerRequestFilter` in `consent` runs **after** authentication, for authenticated requests only.
- **Allowed** without acceptance: `GET /api/v1/me`, `GET /api/v1/me/terms`, `POST /api/v1/me/terms/accept`, `POST /api/v1/auth/logout`, `POST /api/v1/auth/logout-all`, `DELETE /api/v1/me`, `POST /api/v1/me/export`.
- Otherwise, if the user has not accepted the current version of **both** `TERMS` and `PRIVACY`: 403 `TERMS_NOT_ACCEPTED` problem+json.
- "Current" = the latest `published_at` per kind.
- Cache the acceptance per user for 60 s (Caffeine). Evict it on accept.

### Endpoints (`public.yaml`)

| Endpoint | Behaviour |
|---|---|
| `GET /me/terms` | For each kind (TERMS, PRIVACY, DERIVATIVE_RISK): `{kind, currentVersion, title, accepted: bool}`. The body text is fetched by version via `/content/...` later |
| `POST /me/terms/accept {version}` | `version` must be the current version of TERMS or PRIVACY (otherwise 400). Idempotent. Insert into `terms_acceptances` with ip and user agent |
| `POST /me/derivative-risk/ack {version}` | `version` must be the current DERIVATIVE_RISK version. Stored in `terms_acceptances` |
| `consent.api.DerivativeRiskGate.isAcknowledged(UUID userId)` | Java API for WP-13 |
| `GET /me/consents` | Current state per purpose (view `core.current_consents`), with `required` |
| `PUT /me/consents/{purpose} {granted}` | P2/P3/P4 only (P1 → 400 "use account deletion"). Append a row with `source='SETTINGS'`. Publish `ConsentChanged`. The cached state is ≤ 5 min old (FR-014) |
| `consent.api.ConsentQuery.isGranted(UUID userId, String purpose)` | Java API for notification and telemetry |
| `POST /me/export` | `200 application/json` with `{generatedAt, sections: {<section>: ...}}` from every `PersonalDataContributor` bean (FR-017). Max once per hour per user (Redis) |
| `DELETE /me {password}` | Wrong password → 400 (lockout rules from WP-04 apply). Otherwise `requestDeletion`, enqueue the email `ACCOUNT_DELETION_REQUESTED` (new template), return 202 |

### Jobs (`@Scheduled`, cron in config, timezone Asia/Ho_Chi_Minh)

**Deletion job (02:00):**

- For every `DELETION_REQUESTED` user, run all `PersonalDataEraser` beans in `order()`, then `markDeleted`.
- Each user is processed in **its own transaction**: a failure on one user is logged and retried the next night, and does not block the others (ALG-15).
- Batches of 100.

**Unverified cleanup (02:30):**

- `PENDING_VERIFICATION` accounts older than 7 days go through the same erasers, then `markDeleted`.

### Audit

- Publish events that implement `shared.AuditableEvent` (`actorType`, `actorId`, `action`, `targetType`, `targetId`, `detail`): `TermsAccepted`, `ConsentChanged`, `AccountDeletionRequested`, `AccountErased`.
- WP-06 writes them to `core.audit_log`.

## Tests (Testcontainers; `./gradlew build`)

- **Terms gate:** a user who has not accepted gets 403 `TERMS_NOT_ACCEPTED` on a protected endpoint, and 200 on each allowed endpoint. After accepting both, they get 200. After a new TERMS version is published, they get 403 again (FR-012).
- **Accept:** a non-current version gives 400; accepting twice is idempotent.
- **Derivative ack:** stored, and the gate API returns true after it.
- **Consents:**
  - Toggling P2 off then on gives two history rows and a correct current view.
  - P1 → 400.
  - After a change, `ConsentQuery` reflects it within the cache TTL (fake clock).
- **Export:** contains the identity and consent sections; no password hash and no token hashes; second call within an hour → 429.
- **Delete:** a wrong password gives 400. The right password gives 202, all tokens revoked, refresh fails, and the outbox has the email.
- **Deletion job:**
  - `core.users` is scrubbed: no original email, `user_secret` NULL.
  - Tokens are gone; terms rows remain with ip/user agent NULL; status `DELETED`.
  - Login with the old email fails.
  - Make one eraser throw for one user: that user stays `DELETION_REQUESTED` and the others are processed.
- **Unverified cleanup:** an 8-day-old pending account is erased; a 6-day-old one is not.
- **`ModularityTests`** pass.
- **Coverage:** ≥ 80% for `consent`.
