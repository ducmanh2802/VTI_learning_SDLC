# WP-24: R1 release verification (E2E, load, accessibility, AI red-team, release checklist)

| Field | Value |
|---|---|
| Size | L |
| Audit level | **Deep**: release gate |
| Branch | `wp-24-release-verification` |
| Depends on | All other R1 WPs |
| References | PRD 6.1 (LG-01 to LG-11), 3 (all P0 Given–When–Then); SRS NFR-P01 to NFR-P07, NFR-U01, NFR-U02, NFR-AI01 to NFR-AI03, NFR-A04; SDD QAS-01 to QAS-13 |

## Goal

Produce the evidence for every R1 launch gate, and a signed-off release checklist. Any failing gate becomes a numbered defect with an owner. **The beta is not opened while a gate fails.**

## In scope

- `tests/e2e/**` (full-stack Playwright against the compose stack)
- `tests/load/**` (k6 scripts)
- `tests/ai-redteam/**` (end-to-end red-team runner)
- `docs/release/R1-checklist.md`
- `docs/workpackages/reports/WP-24.md`
- Small bug fixes **only** with a linked defect id and a regression test. Anything bigger becomes a new WP.

## Work

### LG-01: functional

- One Playwright test per PRD **P0** story, **named after the story id** (for example `US-040 MP buy fills`). They run against the real stack:
  - compose `app` profile;
  - migrator;
  - ingestion with fixtures or a recorded provider mode: add a `PROVIDER_MODE=replay` option in Analytics if missing, so tests do not depend on the live market;
  - LLM fake mode (`LLM_PROVIDERS=fake`), which needs a fake provider selectable by config.
- Each test asserts its Given–When–Then.

### LG-02: performance (k6, free)

| Scenario | Target |
|---|---|
| 100 virtual users on read endpoints (overview, quote, symbol page APIs, watchlists) for 10 min | p95 ≤ 500 ms, p99 ≤ 1.5 s, error rate < 1% |
| Overview | p95 ≤ 1 s |
| Paper order placement, 20 VUs | p95 ≤ 500 ms |

Run them on the dev machine with the prod-like limits from WP-22, and record the hardware.

### LG-03: security

- OWASP ZAP baseline (Docker) against the prod-like stack: no High alerts.
- Dependency scans:
  - Gradle: OWASP dependency-check or `gradle dependencyCheckAnalyze` (free);
  - Python: `pip-audit`;
  - Node: `pnpm audit`.
- 0 Critical alerts; list any High with a decision.
- Secret scan: green.
- Fill in the ASVS L1 checklist (`docs/release/asvs-l1.md`), each item with evidence or "n/a".

### LG-04: AI safety

- **`tests/ai-redteam/run.py`** sends ≥ **300** prompts through the real chat pipeline, using the founder's free LLM keys when available:
  - the 150 WP-15 questions;
  - 150 new ones: jailbreaks, role-play, multi-turn style, English, no diacritics.
- **Pass criteria:**
  - every answer is REFUSED, or a PUBLISHED answer that passes a **second, independent** reco/profit scan;
  - **0** leaks;
  - PII test: 50 prompts with emails/phones → 0 PII in the LLM payloads, verified by a recording fake proxy.
- **Fallback rate** over 3 days of normal summary use (or a 200-symbol batch): ≤ 10%.

### LG-05: data

- 5 consecutive trading sessions of real ingestion (or as many as fit before the release date; document the count): ≥ 99% successful cycles from `market.ingestion_runs`.
- Fail-closed E2E: stop the provider → the UI shows stale states, never zeros.

### LG-06: coverage

Collect the coverage reports from every service. The thresholds of each WP must hold.

### LG-07: ledger

Reconciliation runs show 0 mismatches over 5 days of simulated trading by a bot that places random valid orders (the test harness only, never in production).

### LG-08: accessibility

axe on every route: 0 serious/critical.

### LG-09: operations

- WP-22 drill passes.
- An uptime monitor is configured (founder action: document it).
- The runbooks are reviewed.

### LG-10: legal

Checklist items needing founder/legal evidence:

- the OQ-018 opinion;
- terms, privacy and derivative-risk texts published;
- `beta_invite_only` on.

Mark these "pending founder" until provided.

### LG-11: cost

List every external service, its plan and its cost (must be 0 VND).

## Acceptance

- `docs/release/R1-checklist.md` lists LG-01 to LG-11 with status (PASS / FAIL / PENDING-FOUNDER), evidence links (CI runs, reports) and the defects found.
- Every FAIL has a defect id, an owner and a target WP.
