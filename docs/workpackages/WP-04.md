## Goal

Implement every `identity` endpoint of `contracts/openapi/public.yaml`, so that a person can register with an invite, verify their email, log in on web or mobile, refresh, log out, and reset or change the password. Follow the security rules exactly.

## In scope

- `services/core/src/main/java/vn/stockai/core/identity/**`
- `.../consent/**`: only the `UserRegistered` listener described below
- `.../notification/**`: only the email outbox minimum described below
- Tests under `services/core/src/test/**`
- `contracts/openapi/public.yaml`: only to add error code `EMAIL_NOT_VERIFIED` (403) to the `Problem.code` enum and to the login responses
- `services/core/src/main/resources/**` (config, password list, email templates)
- `infra/dev-seed.sql` (new, dev only: one TERMS version, one PRIVACY version, invite `DEV-INVITE-001`; never loaded by the migrator)
- `docs/workpackages/reports/WP-04.md`

## Out of scope

## Design rules

### Module boundaries (SDD 3.4.1)

- `identity` may use `shared` and `notification::api` only.
- Registration publishes `identity.api.UserRegistered(userId, acceptedTermsVersions, optionalConsents, ip, userAgent)`.
- `consent` handles it with a **synchronous** `@EventListener`, inside the same transaction:
  - It checks that `acceptedTermsVersions` contains the **current** version of kind `TERMS` and of kind `PRIVACY` (latest `published_at` per kind).
  - It inserts `core.terms_acceptances` and `core.consents`: P1=true, plus P2/P3/P4 as given, `source='REGISTER'`.
  - If a version is wrong, it throws `ApiException(VALIDATION_ERROR)`, so the whole registration rolls back.

### Email (minimum; WP-18 adds real channels)

- `notification.api.EmailService.enqueue(UUID userId, EmailTemplate template, Map<String,String> params)` inserts `core.notifications` (kind `ACCOUNT` or `SECURITY`) and `core.notification_outbox` (channel `EMAIL`) in the caller's transaction.
- A `@Scheduled(fixedDelay = 2000)` `OutboxDispatcher` sends `PENDING` EMAIL rows through an `EmailChannel` interface:
  - Retry backoff 10 s / 60 s / 5 min, then `FAILED`.
  - The only implementation in this WP is `LogEmailChannel`: `dev` and `test` profiles, logs subject + body.
- Templates are in Vietnamese, under `resources/email/*.txt`, with placeholders:
  - `VERIFY_EMAIL` (link `${app.public-base-url}/verify-email?token=...`)
  - `ACCOUNT_EXISTS`
  - `RESET_PASSWORD` (link `.../reset-password?token=...`)
  - `PASSWORD_CHANGED`
  - `ACCOUNT_LOCKED`

### Tokens and passwords

| Item | Rule |
|---|---|
| Passwords | Argon2id: `Argon2PasswordEncoder.defaultsForSpringSecurity_v5_8()` + BouncyCastle `bcprov-jdk18on` |
| Password policy (FR-002) | 10–128 chars; not in the common-password list; not equal to the email local part |
| Password list | `resources/security/common-passwords.txt`: SecLists `Passwords/Common-Credentials/10k-most-common.txt`, MIT licence; add the licence line to the README |
| Email tokens | 32 random bytes from `SecureRandom`, base64url; store only SHA-256 (`core.email_tokens.token_hash`); single use (`used_at`) |
| Email token expiry | VERIFY_EMAIL 24 h; RESET_PASSWORD 30 min |
| Access token | JWT RS256, 15 min; claims `sub`, `role`, `plan`, `iat`, `exp`, `jti`; signed with `app.jwt.private-key-pem` (dev/test: the same ephemeral keypair WP-03 creates; refactor into one `JwtKeys` bean) |
| Refresh token | 32 random bytes base64url, opaque; stored hashed in `core.refresh_tokens` with `family_id`, 30-day expiry |
| Rotation | Every use: revoke the presented token, insert a new one in the same family, set `replaced_by` |
| Reuse | Presenting a revoked or replaced token revokes the **whole family**, writes `security_events.TOKEN_REUSED`, returns 401 `TOKEN_REUSED` |

**Refresh token delivery:**

- `client=WEB`: cookie `refresh_token`; `HttpOnly; Secure; SameSite=Strict; Path=/api/v1/auth; Max-Age=2592000`. The token is **never** in the body.
- `client=MOBILE`: in the body as `refreshToken`.
- Refresh accepts the cookie first, then the body.

### Login (UC-002, SD-02)

1. Rate limit 10 per minute per IP, using a Redis counter `rl:login:{ip}` with a 60 s TTL. Over the limit → 429 `RATE_LIMITED` with `Retry-After`.
2. Look up the user.
   - If not found or the password is wrong, run the password check against a fixed dummy Argon2 hash, so the response time does not reveal whether the email exists.
   - Return 401 `UNAUTHENTICATED`, "Email hoặc mật khẩu không đúng".
3. Wrong password: increment `failed_login_count` (reset after 15 min of no failures). On the 5th failure within 15 min:
   - set `locked_until = now + 15 min`;
   - enqueue `ACCOUNT_LOCKED`;
   - return 423 `ACCOUNT_LOCKED`.
   While locked, return 423 without checking the password.
4. Status checks:
   - `PENDING_VERIFICATION` → 403 `EMAIL_NOT_VERIFIED`.
   - `SUSPENDED`, `DELETION_REQUESTED`, `DELETED` → 403 `FORBIDDEN`.
5. `role=ADMIN`: call `identity.internal.AdminSecondFactor.verify(user, totp)`. In this WP its only implementation **always rejects** (WP-06 adds TOTP).
6. Success: reset counters, write `security_events.LOGIN_OK` (ip, user agent), issue tokens.

### Registration (UC-001, FR-019)

All of this happens in one transaction:

1. Validate the payload.
2. If the feature flag `beta_invite_only` is enabled (read `core.feature_flags`), check the invite:
   - Lock the row with `SELECT ... FOR UPDATE` by SHA-256 of the code.
   - The invite is valid only if it is not revoked, not expired, and `used_count < max_uses`.
   - Invalid → 403 `INVITE_INVALID`, the same response for every reason.
3. If the email already exists (`status <> 'DELETED'`): enqueue `ACCOUNT_EXISTS` for that user, return 202 **identical** to success, and do **not** consume the invite.
4. Otherwise:
   - insert the user (`PENDING_VERIFICATION`) and the redemption;
   - `used_count += 1`;
   - publish `UserRegistered` (consent rows are written synchronously);
   - insert the VERIFY_EMAIL token and enqueue `VERIFY_EMAIL`;
   - return 202.

Then:

- **`resend-verification`:** max 3 per hour per email (Redis). Always returns 202.
- **`verify-email`:** valid token → `status=ACTIVE`, `email_verified_at=now`; otherwise 400 `VALIDATION_ERROR`, "Liên kết đã hết hạn hoặc đã được sử dụng".
- **`password/forgot`:**
  - Always returns 202.
  - Sends RESET_PASSWORD only to `ACTIVE` users.
  - Max 3 per hour per email.
- **`password/reset`:**
  - Check the token and the password policy.
  - Update the hash and revoke all refresh tokens of the user.
  - Write `security_events.PASSWORD_RESET` and enqueue `PASSWORD_CHANGED`.
- **`password/change`:**
  - Authenticated; the current password is required, a wrong one → 400 `VALIDATION_ERROR`.
  - Same effects as reset, except tokens: keep the current refresh token and revoke the others.
- **`logout`:** revoke the presented refresh token (cookie or body); clear the cookie (`Max-Age=0`).
- **`logout-all`:** revoke every refresh token of the user.
- **`GET /me`, `PATCH /me`:**
  - `PATCH /me` may change only `displayName` (≤ 60 chars) and `defaultAlertChannels` (subset of `IN_APP`, `EMAIL`, `PUSH`).

### Persistence

- JPA entities only for the tables that `identity` owns: `users`, `email_tokens`, `refresh_tokens`, `security_events`, `invites`, `invite_redemptions`.
- They must pass `ddl-auto=validate` against `V1__baseline.sql`.
- Use `Clock` for every timestamp.

## Tests (all in `./gradlew build`; Testcontainers Postgres + Redis, migrations applied)

### Registration

- Valid invite → 202, user `PENDING_VERIFICATION`, `used_count=1`, terms and consent rows written, VERIFY_EMAIL outbox row.
- Invalid, expired, revoked or used-up invite → 403 `INVITE_INVALID`; nothing written.
- Flag disabled → registration works without an invite.
- Existing email → 202 with the same body; `ACCOUNT_EXISTS` enqueued; `used_count` unchanged.
- Weak password (short / common / equals local part) → 400 with a field error.
- Wrong terms version → 400 and full rollback (no user row).

### Verification

- Valid token activates the account.
- A used or expired token → 400.
- `resend-verification` is limited to 3 per hour.

### Login

- Success for WEB:
  - Body has no `refreshToken`.
  - `Set-Cookie` has `HttpOnly`, `Secure`, `SameSite=Strict`, `Path=/api/v1/auth`.
- Success for MOBILE: body has `refreshToken`.
- Wrong password → 401.
- 5 failures → 423, `locked_until` set, `ACCOUNT_LOCKED` enqueued.
- 11 requests in a minute from one IP → 429.
- `PENDING_VERIFICATION` → 403 `EMAIL_NOT_VERIFIED`.
- `ADMIN` → rejected (no TOTP implementation yet).

### Access token

- The issued token works on a protected endpoint (`GET /me`).
- An expired token → 401 (use a fixed `Clock`).

### Refresh

- Rotation returns a new token, and the old one is marked `replaced_by`.
- **Reuse of the old token → 401 `TOKEN_REUSED` and every token of the family is revoked** (counter-example test).

### Logout

- `logout` revokes the current token only.
- `logout-all` revokes every token.

### Password

- **Forgot:**
  - unknown email → 202, no outbox row;
  - known `ACTIVE` email → 202 and RESET_PASSWORD enqueued.
- **Reset:**
  - success → refresh tokens revoked, `PASSWORD_CHANGED` enqueued;
  - token expired after 30 min → 400 (use `Clock`).
- **Change:** wrong current password → 400; success → other sessions revoked.

### Other

- **`PATCH /me`:** an invalid channel value → 400.
- **Outbox dispatcher:**
  - `LogEmailChannel` receives the message;
  - a failing channel is retried with backoff and then marked `FAILED`.
- **`ModularityTests`** still pass, so there is no `identity → consent` dependency.
- **`ContractPathsTest`** still passes.
- **JaCoCo:** ≥ 80% line coverage for `vn.stockai.core.identity`.
