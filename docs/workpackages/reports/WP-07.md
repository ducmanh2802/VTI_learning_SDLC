## Deviations from the brief

- **Step 4 / acceptance 5 (generated models)**: deferred, because `contracts/openapi/dist/internal.yaml` does not exist yet (WP-02 is written in parallel). The scripts and the exact command are in place, the CI step is written and is skipped while the contract file is absent (`if: hashFiles('contracts/openapi/dist/internal.yaml') != ''`), and the hand-written payload models of the health endpoints live in `api/schemas.py` until the generated ones exist.
- **The generated file is excluded from ruff lint** (`per-file-ignores` for `src/analytics/api/models_generated.py`), because generated code is not our code; it is still checked by `ruff format --check`.
- **Three import-linter contracts use the TOML "array of tables" syntax** (`[[tool.importlinter.contracts]]`) instead of the INI syntax of SDD 3.4.2, because the tool reads `pyproject.toml` that way. The layer list, the source modules and the forbidden modules are exactly those of SDD 3.4.2.
- **`include_external_packages = true`** in the import-linter configuration: the `quant-pure` contract forbids external packages (`httpx`, `redis`, `sqlalchemy`), which the tool only checks when the external packages are part of the graph.
- **`mypy` needs `ignore_missing_imports` for `apscheduler` and `asyncpg`**: neither ships type information, so our own code is still fully checked (`--strict`).
- **The readiness failure answers with an RFC 9457 document** (`code=DATA_STALE`, 503) whose `errors` array names the failing component, instead of a plain body: every error of the API must be a problem document (AGENTS.md 6), and `DATA_STALE` is the only 503 code of the SDD 3.6.1 table.
- **The heartbeat job fires immediately at start-up and then every 60 s**, so the "alive" proof is visible within seconds instead of after a full minute (acceptance 8 allows 70 s).
- **The API problem titles and details are in English**: the internal API is not shown to end users, Core is the layer that renders user-facing text.
- `infra/.env` (git-ignored) was updated locally with the new variables so that the dev compose works; it is not committed.

## Questions / open issues

- **WP-02 dependency**: the internal contract is missing, so `api/models_generated.py` does not exist yet and acceptance 5 stays open. The health endpoints currently use hand-written models (`api/schemas.py`); they should be replaced by the generated ones (or kept, if the contract defines them) when the contract is bundled, and the `Problem` schema of the contract should be checked against `api/errors.py` (field names `type`, `title`, `status`, `detail`, `code`, `correlationId`, `errors`).
- **`Problem.type` URI**: we answer with the relative URI `/errors/<code-in-kebab-case>` (the SDD example uses an absolute `https://<host>/errors/...`). Please confirm which form the contract uses.
- **503 code**: `DATA_STALE` is used for "a dependency does not answer" because SDD 3.6.1 has no `SERVICE_UNAVAILABLE`. If WP-02 prefers another code, only `common/errors.py` and the mapping in `api/errors.py` have to change.
- **`errors` array for component failures**: the readiness failure reuses the optional `errors` array of `Problem` (`{field: "redis", message: ...}`). If the contract prefers another shape (for example a `components` object), the ready route has to change.
- **Settings variable `ENV`**: the runtime environment is read from `ENV` (the brief only names `settings.env`); `APP_ENV` in `.env` feeds it in compose. Please confirm the name, since `ENV` is a Dockerfile keyword and might be confusing.
- **`SERVICE_TOKEN` rotation**: the brief mentions a rotatable shared secret; this WP only implements the comparison. Rotation support (two valid tokens, grace period) is not implemented and would need a requirement in the SRS.
- **SQLAlchemy is a runtime dependency but is not used yet**: the readiness probe uses `asyncpg` directly to stay cheap; SQLAlchemy will be used by the repository layer of `marketdata` (WP-08/WP-10). Flag it if the founder prefers to drop it from WP-07.
